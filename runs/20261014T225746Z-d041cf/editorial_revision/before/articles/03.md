# Make the next agent task bounded, inspectable, and affordable

*As of 2026-10-14.*

The strongest practical implication of the supplied evidence is to evaluate one bounded task before expanding autonomy. Define what should be delivered, state how to check it, retain the results, and include human testing and correction in the cost. This is a proposed evaluation workflow, not a proven productivity recipe: no supplied comparison establishes that it improves completion rates. Its purpose is to make the next attempt easier to assess, including when the attempt fails. [03-c5]

## Put the real checks where the agent can find them

For a Copilot repository, a reasonable first experiment is to record actual testing expectations in `.github/copilot-instructions.md`. GitHub describes this file as a place for repository-wide guidance, including testing and validation. Where useful, its quality-checks skill example offers a way to package the relevant test and lint commands with explanations of what they check and how to troubleshoot failures. [03-c1] ([GitHub, “GitHub Copilot app for Beginners: How to teach Copilot about your codebase”](https://github.blog/ai-and-ml/github-copilot/github-copilot-app-for-beginners-how-to-teach-copilot-about-your-codebase/), published 2026-10-12T17:43:59Z.)

The important word is “actual.” Record checks you understand and can examine, rather than writing an impressive-sounding testing requirement without a way to assess it. In this proposal, the instruction file describes expectations; a `.github/skills/quality-checks` folder and its `SKILL.md` can describe the procedure. Neither is evidence that the procedure ran or passed. Guidance is an input to the task, not a substitute for its outputs. [03-c1]

## Inspect delivery before trusting the status

GitHub’s September availability report provides a concrete reason to distinguish instructions and status from delivered work. It acknowledges an incident in which Copilot code review reported successful completion without producing the review. GitHub says it resolved the incident and advised customers to request affected reviews again. [03-c2] ([GitHub, “GitHub availability report: September 2026”](https://github.blog/news-insights/company-news/github-availability-report-september-2026/), published 2026-10-14T20:01:35Z; incident locator: “September 28 21:16 UTC (lasting 52 minutes)”.)

The proposed check is straightforward: verify that the requested review arrived before using its completion status as evidence. For reviews affected by that incident, the source’s advice was to request them again—not to assume the missing output was equivalent to a clean review. Future reliability reporting is more useful to this assessment if it demonstrates delivered reviews, rather than merely successful jobs. [03-c2]

## Make diagnosis cover the relevant work

If the task is profiling a threaded Python app, check whether the profile includes the threads doing the work. Willison reports that sampling all threads was essential in his web-edit example: 95.1% of recorded stacks came from AnyIO’s worker thread and would have been missed by a main-thread-only profile. He also presents a flame graph and heatmap, diagnostic views to inspect before choosing an optimization. [03-c3] ([Simon Willison, “Profiling web-edit with Python 3.15: flame graphs and source heatmaps”](https://simonwillison.net/2026/Oct/12/python-3-15-web-edit-profiling/), published 2026-10-12T16:58:00Z.)

This is a conditional check, not a prediction that your app has the same bottleneck. The transferable proposal is to ask whether a diagnostic artifact covers the execution context relevant to your question. Producing a graph is only part of that assessment; interpreting its coverage remains necessary. Willison’s diagnostic judgment may not transfer directly to a beginner. [03-c3]

## Bound the attempt before assuming the budget will hold

HTML All The Things supplies an attributed contrast between short agent tasks with periodic check-ins and longer orchestration that exhausted usage. One host describes tasks mostly under five minutes, at most 15, followed by check-ins. Another reports burning through usage and returning to smaller tasks. These accounts support trying bounded work first, not a universal time limit, quota, or best-model recommendation. [03-c4] ([HTML All The Things, “AI’s Biggest Problem Isn’t Intelligence Anymore”](https://www.htmlallthethings.com/podcast/ais-biggest-problem-isnt-intelligence-anymore), published 2026-09-26T13:00:00Z; s00081 and s00088 for task length and check-ins; s00136 and s00140 for exhausted usage and smaller tasks.)

The hosts are agency practitioners, so their decomposition of work may not fit a beginner’s task. Treat their experience as a reason to define a stopping budget and check-in points for your own trial, not as proof that a subscription will sustain a longer cycle. [03-c4]

## Evaluate one complete cycle

For the next trial, define one observable outcome, specify its checks, retain their outputs, and record agent usage alongside human testing and correction time. Examine that complete cycle before expanding the task. Willison’s observation that goal-level token consumption matters more than token prices supports this broader accounting. ([Simon Willison, “llm-gemini 0.35”](https://simonwillison.net/2026/Oct/13/llm-gemini/), published 2026-10-13T22:28:54Z.) [03-c5]

Instructions can be ignored, tests can miss bugs, and additional review adds effort. An individual must bear that assessment cost rather than distribute it among specialists. Start with checks you understand; another model’s agreement should not replace that understanding. The next evidence worth seeking is repeatable small-project results that include failed attempts and total effort—not just completion messages or attractive prices. [03-c5]
