# Review activity is not the same as verified correctness

*As of 2026-10-15*

An AI review can produce criticism, prompt an edit or suggest a repair. Those are different outcomes from confirming a defect and establishing that the repair is correct. The current evidence spans a benchmark, a product announcement and a practitioner's experimental habit. Each illuminates part of review, but their combination does not close the gap between receiving criticism and delivering correct software. For a small project, the defensible interpretation is to treat AI criticism as a candidate finding until its relevance and behavior have been checked. [02-c5]

## Ask which changes a benchmark represents

GitHub describes ReviewBench as containing 219 pull requests from 187 public open-source-licensed repositories across 19 languages. It says language and repository-size distributions closely match GitHub overall, but identifies a deliberate adjustment: reducing the representation of tiny, single-file changes in favor of more substantive, multi-file reviews. ([GitHub, “ReviewBench: An open benchmark for AI code review,” 2026-10-05](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/).) [02-c1]

That makes task selection part of interpreting results. A developer considering assistance with a tiny solo-project edit should not assume that matching the benchmark's language is enough to establish relevance. The source itself says change size was reweighted. This is not a reason to dismiss ReviewBench; it is a reason to ask how closely its review tasks resemble the change under consideration. [02-c1]

## A response metric is not a correctness check

GitHub defines “addressed rate,” its online counterpart to precision, as the percentage of Copilot code-review comments that an LLM judges prompted a corresponding code change. The judgment draws on the diff, discussion thread, reactions, resolution state and post-review code. In plain terms, the metric estimates whether developers acted on comments. It does not independently establish that those comments identified real defects or that subsequent edits removed them. ([GitHub, “ReviewBench,” 2026-10-05](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/).) [02-c2]

GitHub also acknowledges a separate measurement limitation: a fixed “golden set,” or expected list of findings, becomes incomplete as systems discover issues its creators did not anticipate. That creates a genuine tension. Scoring only expected findings may overlook useful discoveries, while measuring a developer's response still leaves correctness unresolved. Neither limitation makes evaluation pointless; both limit what a score can support. [02-c2]

## Test scaffolding is another intermediate output

Fireship's October 15 sponsored segment describes renaming functions and scaffolding tests on an old side project in a few minutes for no model-usage charge. ([Fireship, 5:12–5:23](https://www.youtube.com/watch?v=l3L_lETiSzc&t=312s).) The described result is generated code and test scaffolding. The segment does not present test-run results or an independent check that behavior survived the rename. That distinction parallels the review metrics: an output can be concrete without establishing correctness. JetBrains sponsors the segment, and the narrator's timing and cost are self-reported. They do not account for all verification effort or establish the same access terms for every reader. [02-c6]

## A second critic remains a critic

Willison reports trying adversarial review in his own projects: asking a model to find flaws and sometimes playing Claude and GPT against each other. His October 13 account establishes that he is experimenting with this practice. It does not supply a measured improvement in defect detection, a review-cost comparison or artifacts establishing the outcome of those reviews. ([Simon Willison, “Redesigning source control at Anthropic,” 2026-10-13](https://simonwillison.net/2026/Oct/13/redesigning-source-control-at-anthropic/).) [02-c3]

The practice is relevant as a way to request criticism, not as independent confirmation that the criticism is right. An experienced practitioner's willingness to try a second reviewer should not be converted into evidence that a beginner will obtain more reliable software from the same arrangement. That transfer remains unestablished here. [02-c3] [02-c5]

## Actionable fields are not detection results

Cursor says Security Review looks for injection across SQL, command and template surfaces, plus authentication and authorization bypasses, including checks that stopped running after a refactor. It promises findings with severity, an attack path and a proposed fix. These are advertised targets and output fields—not an evaluation of how many real vulnerabilities the system finds or misses. ([Cursor, “Rollouts and Security Review,” 2026-09-23](https://cursor.com/changelog/rollouts-and-security-reviewer).) [02-c4]

An attack path can make an allegation more concrete, but a concrete allegation remains something to verify. A researcher interviewed by GitHub puts the principle directly: “The main thing I’d say is to always verify what the AI gives you and never submit a finding you haven’t confirmed yourself.” ([GitHub, bug-bounty researcher interview, 2026-10-08](https://github.blog/security/how-one-bug-bounty-researcher-chooses-the-features-they-investigate/).) [02-c5]

The synthesis is therefore a separation, not a ranking. ReviewBench concerns evaluation and inferred response; Willison describes a review habit; Cursor specifies promised findings. GitHub and Cursor also have commercial interests in the tools they discuss. None of these sources alone demonstrates a confirmed defect followed by a correct repair, and none supplies representative first-time-user or unsuccessful-project outcomes. The acceptance criterion should remain checked behavior, not review activity. [02-c5]
