# Beyond code generation: remote control, security review and runtime inspection

*As of 2026-10-15*

Recent AI coding developments are worth examining for what they add around implementation, rather than treating them as proof that software now finishes itself. Cursor has announced remote interaction with local agents and repository-enabled security review. Simon Willison reports using Codex to inspect an application's execution. Alongside those developments, GitHub has explained an incident in which code-review jobs reported success without delivering reviews. Together, these sources support an output-focused question: what inspectable result did the assistant actually leave behind? [01-c5]

## Remote supervision is still local execution

Cursor's October 6 announcement says its iOS app can display local agents running on a developer's computer and let the developer message them. The distinction is important: this is remote interaction, not a transfer of execution to the cloud. Cursor explicitly says the agent continues running on the computer, which must remain on and online. ([Cursor, “Remote control for local agents,” 2026-10-06](https://cursor.com/changelog/remote-control-local-agents).) [01-c1]

For an individual developer, the capability to investigate is therefore supervision away from the keyboard. It does not, on the supplied evidence, remove dependence on the original machine or demonstrate that the agent needs less supervision. Being able to see what an agent is doing and send another message broadens the interface to the work; it does not establish that the work is correct. That is an interpretation of the announced control, not a measured outcome from using it. [01-c1] [01-c5]

## A review format, with access restrictions

Cursor's September 23 Security Review announcement describes enabling review for selected repositories. Each finding is supposed to include a severity, an attack path and a proposed fix. An attack path is the account of how the reported problem could be reached or exploited. Draft pull requests—proposed changes still marked as drafts—are skipped, and the announcement offers access on Teams and Enterprise plans. ([Cursor, “Rollouts and Security Review,” 2026-09-23](https://cursor.com/changelog/rollouts-and-security-reviewer).) [01-c2]

Those details establish an announced output format and boundaries, not detection effectiveness. For someone building a small project alone, access is part of the evaluation: the announcement does not resolve whether purchasing an eligible plan is practical. Nor does a structured finding establish that the alleged vulnerability exists or that its proposed repair is correct. The useful development is a review output that can be inspected, rather than evidence that security checking has been settled. [01-c2] [01-c5]

## Inspecting execution, not demonstrating a speedup

Willison's October 12 account provides a different kind of example. He reports having Codex run Python 3.15's profiler against his web-edit application, producing an example flame graph and heatmap—visual profiling outputs for inspecting execution. This is a concrete account of an assistant helping investigate running software, rather than only generating an implementation. ([Simon Willison, “Profiling web-edit with Python 3.15,” 2026-10-12](https://simonwillison.net/2026/Oct/12/python-3-15-web-edit-profiling/).) [01-c3]

The boundary matters. The account demonstrates neither a completed optimization nor a measured saving in delivery time. It is also an experienced maintainer's report about his own application, without a controlled comparison or complete accounting of testing and correction effort. A developer with basic skills may still need additional setup and interpretation; the example does not establish reproducibility for that audience. [01-c3]

## “Completed” was not “delivered”

GitHub's availability report, published October 14, supplies a counterweight. Explaining its September 28 Copilot code-review incident, GitHub says some jobs could not build a review but nevertheless reported successful completion. It says missing review results were not detected because monitoring was lacking. GitHub reports reverting the change and advising customers to request affected reviews again. ([GitHub, “GitHub availability report: September 2026,” published 2026-10-14; incident section: September 28, 21:16 UTC](https://github.blog/news-insights/company-news/github-availability-report-september-2026/).) [01-c4]

This is GitHub's own account of its incident and mitigation, not an independent reliability assessment. It nevertheless makes the distinction between a completion signal and a delivered result explicit. [01-c4]

The combined implication is modest: judge these developments by actual agent changes, a delivered review or a runtime profile. Cursor and GitHub describe products they sell; Willison supplies a first-person example. These sources do not provide independent evidence of solo-project completion gains, representative beginner outcomes or the experience of abandoned projects and accessibility users. Broader development actions are worth investigating, but finishing still needs an inspectable result—not merely an agent saying it is done. [01-c5]
