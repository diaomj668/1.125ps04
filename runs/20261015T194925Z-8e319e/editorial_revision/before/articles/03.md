# Try one bounded task—and account for the work needed to verify it

*As of 2026-10-15*

For an individual developer, the defensible next step is a small, reversible trial—not immediate adoption of a more elaborate agent workflow. Define what would count as success, inspect the delivered evidence and record the effort required to reach an acceptable result. This is a proposed evaluation approach, not a workflow tested here or a claim that one task size is best. The aim is to measure verified delivery cost rather than generation alone. [03-c5]

## Start with one convention

GitHub's beginner tutorial recommends adding repository guidance in `.github/copilot-instructions.md`, including conventions and expectations for testing and validation. Its closing advice is deliberately incremental: choose one convention repeatedly explained to Copilot and see how it applies that guidance to the next task. ([GitHub, “How to teach Copilot about your codebase,” 2026-10-12](https://github.blog/ai-and-ml/github-copilot/github-copilot-app-for-beginners-how-to-teach-copilot-about-your-codebase/).) [03-c1]

A bounded trial could therefore begin with one convention and explicit validation commands, rather than every available customization. Inspect whether the resulting change follows the instruction and whether the requested validation actually happened. The file communicates guidance; it should not be treated as an enforced guarantee. Keeping the trial narrow makes that particular question the object of evaluation, without claiming that the setup will improve every subsequent task. [03-c1]

## Check what a profile actually observed

Verification setup deserves attention of its own. In Willison's web-edit profiling report, 95.1% of recorded stacks came from AnyIO's worker thread. He says a main-thread-only profile would have missed them. His accompanying Python article explains sampling as periodically capturing stack traces from running processes to estimate where execution time is spent. ([Simon Willison, web-edit profiling report, 2026-10-12](https://simonwillison.net/2026/Oct/12/python-3-15-web-edit-profiling/); [Python 3.15 overview, 2026-10-12](https://simonwillison.net/2026/Oct/12/python-3-15/).) [03-c2]

The proposed check for an assistant's Python performance suggestion is consequently specific: reproduce a relevant workload, include the threads doing the work and then compare the proposed change. A profile's sample frequencies alone do not demonstrate elapsed-time savings. Also check setup requirements rather than copying an example blindly: Willison reports needing `sudo` on macOS to attach the profiler. His result motivates inspecting coverage; it does not establish that another application's useful profile will have the same configuration. [03-c2]

## Make security review a conditional trial

Cursor's announcement offers Security Review on Teams and Enterprise plans, with findings containing severity, an attack path and a proposed fix. Check current access and price before planning a trial around it. On an authorized test copy, the proposed evaluation is to reproduce the reported behavior using the attack path, then check whether the fix removes that behavior without breaking intended use. ([Cursor, “Rollouts and Security Review,” 2026-09-23](https://cursor.com/changelog/rollouts-and-security-reviewer).) [03-c3]

This is not an adoption recommendation. It follows the verification principle expressed by a researcher in GitHub's October 8 interview: never submit an AI finding without confirming it yourself. Access to a reviewer and receipt of a proposed fix are starting conditions for this check, not substitutes for it. ([GitHub, bug-bounty researcher interview, 2026-10-08](https://github.blog/security/how-one-bug-bounty-researcher-chooses-the-features-they-investigate/).) [03-c3]

## Budget for the whole attempt

The HTML All The Things hosts describe contrasting usage experiences. One reports mostly short tasks and no further limit after switching back to another model. The other describes combining shorter steps into longer workflows and exhausting usage. These are attributed experiences, not a controlled comparison or evidence of model superiority. ([HTML All The Things, “AI’s Biggest Problem Isn’t Intelligence Anymore,” 2026-09-26, 04:20–04:44, segments s00076, s00078, s00081; 07:17–07:36, segments s00131, s00132, s00136](https://www.htmlallthethings.com/podcast/ais-biggest-problem-isnt-intelligence-anymore).) [03-c4]

For the next trial, record acceptance checks, delivered outputs, retries, quota use or API spending, and human testing and correction time. Willison's pricing discussion reinforces why a unit price is insufficient: his stated concern is how many tokens a model needs to achieve a goal within an agent workflow. ([Simon Willison, “llm-gemini 0.35,” 2026-10-13](https://simonwillison.net/2026/Oct/13/llm-gemini/).) [03-c5]

Expand only after reviewing that record. Beginners may need substantial verification setup, especially without a useful test suite; experienced practitioners' accounts do not settle that cost. Eligibility, compatibility, permissions, quotas and prices remain checks to perform. None of this evidence proves that another reviewer or paid tool will repay its setup effort. The useful next result is a bounded task whose output and total verification burden you can inspect. [03-c5]
