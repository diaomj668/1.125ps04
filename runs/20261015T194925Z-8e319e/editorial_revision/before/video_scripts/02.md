# Review activity is not the same as verified correctness
As of: 2026-10-15

**Visual direction:** Opening title card for Google Vids or HeyGen. Plan for synthetic narration and display “AI-generated narration.” Introduce a three-stage diagram: criticism → checked defect → checked repair. Keep the arrows visually separate.

**Narration:** This presentation uses an AI-generated voice. As of October 15, 2026, the evidence around AI code review supports a narrow conclusion: tools can produce criticism, benchmarks can assess review tasks, and developers can experiment with another model as a reviewer. None of those facts, by itself, proves that a defect was confirmed or correctly repaired. For a solo developer, that distinction matters more than the number of comments generated.

**Visual direction:** Display “ReviewBench: 219 pull requests / 187 repositories / 19 languages.” Beside it, show “Tiny, single-file changes deliberately reduced.” Do not illustrate these figures as performance scores.

**Narration:** Consider GitHub’s ReviewBench. GitHub describes it as containing 219 pull requests from 187 public, open-source-licensed repositories across 19 languages. A pull request is a proposed code change submitted for review. The benchmark deliberately reduces the representation of tiny, single-file changes in favor of more substantial, multi-file work. That makes its task mix important to examine before applying results to the small edits common in individual projects. Inspectable tasks are useful, but their relevance to your work still needs checking.

**Visual direction:** Animate “Review comment → code change,” then pause before a separate “Confirmed defect removed” box. Label the first arrow “LLM-inferred response.”

**Narration:** Next, look closely at the metric. GitHub defines addressed rate as the percentage of review comments that a language model judges to have prompted a corresponding code change. That is an inferred developer response. It is not independent verification that a defect existed or that the edit removed it. GitHub also acknowledges that a fixed set of expected findings becomes incomplete as systems discover issues its creators did not anticipate. Both qualifications matter when interpreting review scores.

**Visual direction:** Show two generic reviewer cards labeled Claude and GPT, pointing toward the same code change. Caption: “Reported practice; effectiveness not measured here.”

**Narration:** Simon Willison reports trying adversarial review in his own projects: asking a model to look for flaws, sometimes playing Claude and GPT against each other. This establishes an attributed practice, not a measured improvement in defect detection. His account does not provide a review-cost comparison or artifacts that establish its effectiveness.

**Visual direction:** Return to the opening diagram. Highlight “Check relevance” and “Check behavior” between criticism and confirmation.

**Narration:** Treat AI criticism as a candidate finding until you check its relevance and behavior. We cannot infer verified correctness from a comment, an edit, or agreement between reviewers. GitHub built its benchmark with Microsoft and evaluates a product it sells; its separate relabeling used internal senior engineers, not an independent publisher. Experienced practitioners may also be better equipped than beginners to reject plausible but irrelevant criticism. These sources address different stages of review. The unresolved step is confirming the defect and checking the repair.
