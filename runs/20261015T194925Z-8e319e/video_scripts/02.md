# Review activity is not the same as verified correctness
As of: 2026-10-15

**Visual direction:** Opening title card for Google Vids or HeyGen. Plan for synthetic narration and display “AI-generated narration.” Introduce a three-stage diagram: criticism → checked defect → checked repair. Keep the arrows visually separate.

**Narration:**
As of October 15, 2026, the evidence around AI code review supports a narrow conclusion: tools can produce criticism, benchmarks can assess review tasks, and developers can experiment with another model as a reviewer. None of those facts, by itself, proves that a defect was confirmed or correctly repaired. For a solo developer, that distinction matters more than the number of comments generated.

**Visual direction:** Display “ReviewBench: 219 pull requests / 187 repositories / 19 languages.” Beside it, show “Tiny, single-file changes deliberately reduced.” Do not illustrate these figures as performance scores.

**Narration:**
Consider GitHub’s ReviewBench. GitHub describes it as containing 219 pull requests from 187 public, open-source-licensed repositories across 19 languages. A pull request is a proposed code change submitted for review. The benchmark deliberately reduces the representation of tiny, single-file changes in favor of more substantial, multi-file work. That makes its task mix important to examine before applying results to the small edits common in individual projects. Inspectable tasks are useful, but their relevance to your work still needs checking.

**Visual direction:** Animate “Review comment → code change,” then pause before a separate “Confirmed defect removed” box. Label the first arrow “LLM-inferred response.”

**Narration:**
Next, look closely at the metric. GitHub defines addressed rate as the percentage of review comments that a language model judges to have prompted a corresponding code change. That is an inferred developer response. It is not independent verification that a defect existed or that the edit removed it. GitHub also acknowledges that a fixed set of expected findings becomes incomplete as systems discover issues its creators did not anticipate. Both qualifications matter when interpreting review scores.

**Visual direction:** Show two separate boxes: “Generate tests” and “Run tests and check behavior.” Label the example “Fireship; JetBrains-sponsored; October 15.”

**Narration:**
The same distinction applies to test generation. In an October 15 JetBrains-sponsored segment, Fireship's narrator reports renaming functions and scaffolding tests on an old side project in a few minutes for no model-usage charge. Scaffolding tests means creating their starting structure. It does not mean they ran or passed. The segment presents no independent behavior-preservation check. Like a review comment, this intermediate output needs verification before it can count as correct delivery. The sponsor and missing full-effort accounting limit the claim.

**Narration:**
Simon Willison reports trying adversarial review in his own projects: asking a model to look for flaws, sometimes playing Claude and GPT against each other. This establishes an attributed practice, not a measured improvement in defect detection. His account does not provide a review-cost comparison or artifacts that establish its effectiveness.

**Visual direction:** Return to the opening diagram. Highlight “Check relevance” and “Check behavior” between criticism and confirmation.

**Narration:**
Treat AI criticism as a candidate finding until you check its relevance and behavior. We cannot infer verified correctness from a comment, an edit, or agreement between reviewers. GitHub built its benchmark with Microsoft and evaluates a product it sells; its separate relabeling used internal senior engineers, not an independent publisher. Experienced practitioners may also be better equipped than beginners to reject plausible but irrelevant criticism. These sources address different stages of review. The unresolved step is confirming the defect and checking the repair.
